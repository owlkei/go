# HTTP after roadmap 0005

Roadmap 0005 (middlewares, built-in modules, security) measured against `docs/review/http-0004.md`,
this time in production settings: release binaries, JSON request logs written to a file on disk,
GOMAXPROCS 1, 2 and all cores, and the server's CPU time per request.

- **Machine:** the same Intel Core i7-9750H laptop (`Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz`, 12
  logical CPUs, 16 GB). Quieter than for 0004 (load average about 2 at rest, against 4-9), but it
  **throttles**: under full load macOS lowers `CPU_Speed_Limit` (`pmset -g therm`) to 55-75 % within
  about 30 s. The first load round (14 min straight) and the Go benchmarks ran before this was
  noticed; a second straight round ran at a 55 % limit and is discarded (every framework,
  net/http included, at about half the first round's rate). The headline load numbers come from a
  third, "cool" round: every 3 s run starts only when the limit is back at 100 %, and the limit at its
  end was 88-100 % (median 97 %). The 1-minute load average during that round was 2.1-8.6 (median
  3.5), most of it the test itself (`wrk` plus the server).
- **Go:** 1.27.4, darwin/amd64. **Commit:** `eaa34ab` plus the `bench/` changes of this step.
  The 0004 column is commit `ac59463` (0004's measured commit) measured again in this run in a git
  worktree, alternating with the current commit round by round.
- **Rerun:**
  - Go benchmarks: `make bench-compare` (add `-cpu 1,2,12` for the small-machine rows).
  - Load test: `FRAMEWORKS="ginject nethttp gin echo chi fiber" LOGS="on off" PROCS="1 2 all" DURATION=3s CONNECTIONS=64 SCENARIOS="Static Chain" make load`.
    The cool round called it once per framework, log setting, GOMAXPROCS and scenario, in forward
    and then reverse framework order, after waiting for `CPU_Speed_Limit = 100`.
  - Middlewares and modules: `go test -run '^$' -bench . -benchmem -cpu 1,2 -count 5` in each
    package (`loadshed` with `-bench 'Admitted|_Shed$'`, without the L12 / L13 acceptance runs).

## What changed in `bench/`

- `cmd/server` takes `-log`: each framework's request logger writes one JSON line per request to
  stdout, and `load.sh` sends stdout to a file on disk (`LOG_DIR`). Ginject uses its built-in
  logger in JSON with `EnableAccessLog`; Gin `LoggerWithConfig` with a JSON formatter; Echo
  `RequestLoggerWithConfig` through `slog`'s JSON handler; Chi `middleware.Logger` (text: Chi has
  no JSON logger); Fiber `logger.New` with a JSON format. net/http has none.
- The server prints its `getrusage` user + system time on `SIGUSR1`; `load.sh` reads it before and
  after each run and divides by the requests `wrk` completed.
- `load.sh` builds with `go build -trimpath -ldflags="-s -w"`, sets `GOMAXPROCS` per run (`PROCS`)
  and counts the log lines written during each run. No PGO: no profile exists yet.
- The Go benchmarks (`bench_test.go`) are unchanged: no request logger, `io.Discard`-like writer.

## Cost of the request logger

Extra server CPU per request with the logger on, against the same framework with it off (cool
round, better of two runs each):

| GOMAXPROCS | Scenario | Ginject | Gin | Echo | Chi | Fiber |
|---|---|---|---|---|---|---|
| 1 | Static | +23.6 µs | +12.9 µs | +15.7 µs | +18.1 µs | +10.6 µs |
| 1 | Chain | +27.0 µs | +17.2 µs | +17.1 µs | +18.5 µs | +13.1 µs |
| 2 | Static | +14.5 µs | +15.4 µs | +15.3 µs | +16.0 µs | +11.1 µs |
| 2 | Chain | +18.8 µs | +16.7 µs | +16.3 µs | +17.0 µs | +13.2 µs |
| all | Static | +20.9 µs | +34.6 µs | +40.9 µs | +48.5 µs | +31.2 µs |
| all | Chain | +34.8 µs | +39.4 µs | +42.1 µs | +45.8 µs | +34.7 µs |

- **A request log line is the most expensive part of a request** for every framework: it costs
  as much CPU as the rest of the request, and it halves the request rate on one or two cores.
  The other loggers make one `write` system call per line; most of their cost is that call.
- **On all cores Ginject's line is the cheapest** (+21 µs against +31 to +49 µs). The batched,
  asynchronous output makes few system calls; the others contend on the file in each request
  goroutine. With logging on at 12 cores Ginject is the fastest on Static (90k requests per second
  against 47-78k) and on par with Fiber on Chain (70k and 71k, the others 44-60k).
- **On 2 cores it is on par** (+14.5 µs against +11 to +16 µs) although its line is 2-4 times
  longer.
- **On 1 core it is the most expensive** (+24 to +27 µs against +11 to +19 µs), and the rate falls
  to about 70 % of Gin, Echo and Chi. The next section shows why.
- The 0004 follow-up measured +3.9 µs per request at GOMAXPROCS 1 with one goroutine and one
  request at a time. With 64 concurrent connections the cost is six times that, almost all of it
  the scheduling effect below, not encoding.

## The GOMAXPROCS 1 tail

A runtime trace of the release build under the same load (GOMAXPROCS 1, Static, 64 connections,
2 s traced; a scratch program around `bench.NewGinjectAppWithLog`) shows where the time goes:

| Server, GOMAXPROCS 1 | Requests/s | p99 | Time blocked in `net/http.(*connReader).abortPendingRead` | Wait p50 / p99 | New goroutines per request |
|---|---|---|---|---|---|
| Ginject, log on | 15.6k | 151 ms | 74.9 s | 2.4 ms / 5.6 ms | 2.0 |
| Ginject, log off | 28.2k | 14 ms | 0.20 s | 1.2 µs / 32 µs | 1.0 |
| Gin, log on | 17.3k | 20 ms | 0.16 s | 1.5 µs / 22 µs | 1.0 |
| net/http | 32.2k | 6 ms | 0.14 s | — | — |

- net/http starts one background-read goroutine per request and, when the handler returns,
  `finishRequest` waits for it to exit (`abortPendingRead`). That goroutine is created into the
  P's `runnext` slot, so it normally runs at once and the wait is about 1 µs.
- With Ginject's access log, each line that finds the output writer idle starts a new writer
  goroutine (`go s.drain()` in `internal/logpipe`). A new goroutine also takes `runnext` and pushes
  the background reader to the back of the run queue, behind the other connections. Every request
  then waits about 2.4 ms for its own background reader: 75 s of blocked goroutine time in 2 s.
  The trace counts 2.0 new goroutines per request (the reader and a writer) against 1.0 without
  the log.
- On two or more cores another P runs the reader, so the effect disappears (p99 3-6 ms).
- This is the "one writer wake-up per line" left open in 0004, now measured on a real server: on
  one core it costs the most CPU and a 100-300 ms p99. The backlog's log batching delay (one
  wake-up per batch instead of per line) would remove most of it. Waking a parked writer instead of
  starting one would likely not help by itself: a goroutine made runnable by another one also
  takes `runnext`.

- Ginject costs about 6-8 µs of CPU per request more than net/http at 1 and 2 cores, and 14-15 µs
  at 12 cores. In 0004 (12 cores, a much busier machine, 5 s runs) the rate ratio was 84 % for both

## What is left

- **GOMAXPROCS 1 with the access log on:** p99 95-300 ms and about +10 µs of CPU per request over the
  other loggers, from one new writer goroutine per access line (the trace above). The backlog's log
  batching delay is the fix to design; it now has a measured target: the 2.4 ms
  `abortPendingRead` wait per request at GOMAXPROCS 1.
- **Request-scope bytes:** still 721 B per Static request against net/http's 2 B; Static remains
  8× net/http in the micro benchmark (the reflection floor of design 0006 Q1 plus the scope).
- **Measurement:** this laptop throttles within 30 s of full load. Future reports should keep the
  cool-round method (short runs that start at a 100 % speed limit, alternating order) or use a
  desktop or a cloud VM with fixed clocks.
- Unchanged from 0004: 0003 H1 / H2 (pooled encoders, shared header slices), L2, L3, L6, L10, the
  HTTP half of L8.
