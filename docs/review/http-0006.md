# HTTP after roadmap 0006

Roadmap 0006 (log writer wake-up, `loadshed` probes and queue order, review follow-ups) measured
against `docs/review/http-0005.md` with the same production settings: release binaries, JSON
request logs written to a file on disk, GOMAXPROCS 1, 2 and all cores, and the server's CPU time
per request. The reference points are the ones in `bench/README.md` › "How the measurements stay
fair": net/http with no logger is the floor, the target is the **best of Gin, Echo and Chi** in the
same run with their loggers on, and Fiber (fasthttp) is shown for reference only.

- **Machine:** the same Intel Core i7-9750H laptop (`Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz`, 12
  logical CPUs, 16 GB), shared with a browser and an editor (Chrome and VS Code renderers at
  10-20 % of a core each). It **throttles**: every run below waited for `CPU_Speed_Limit = 100`
  (`pmset -g therm`, up to 90 s) before it started. The limit at the end of each run and the
  1-minute load average:

  | Batch | Runs | Speed limit at the end | Load average |
  |---|---|---|---|
  | Owlkei Go against `0cdeef1`, GOMAXPROCS 1 and 2 | 40 | 93-100 % (median 100 %) | 4.1-7.1 (median 5.3) |
  | All frameworks, three rounds | 108 servers (54 calls) | 24-100 % (median 82 %) | 1.9-5.6 (median 2.8) |
  | Owlkei Go against `0cdeef1`, all cores | 16 | 86-100 % (median 88 %) | 2.0-4.3 (median 2.8) |
  | `logpipe` and `loadshed` benchmarks | 24 passes | 77-93 % | 2.1-4.4 |

  In the first framework round the GOMAXPROCS-all runs started at a 26-84 % limit after the
  waits timed out (every framework, net/http included, ran at a third to half of its later rate).
  Those runs lose every best-of comparison and change no cell. Apart from them, a run's rate spread
  about ±5 % around the median, and one run in five or six had a p99 outlier of 10-70 ms. That
  happened to every framework: Gin 46 ms, Chi 32 ms and Fiber 71 ms at GOMAXPROCS 1. **Noise
  level:** moderate. It is enough to blur differences under about 10 % in requests per second.
  It cannot hide the GOMAXPROCS 1 tail that 0005 measured, which was 20-30 times the others.
- **Go:** 1.27.4, darwin/amd64. **Commit:** `9b130a4` (roadmap 0006 steps 1-5). The 0005 column is
  commit `0cdeef1` (roadmap 0005 end, before the log writer change), measured again in this session
  from a git worktree. Its rounds alternated with `9b130a4` (the order swapped each round), and both
  builds used the same `bench/` code.
- **Rerun:**
  - Load test: `FRAMEWORKS=<one> LOGS="on off" PROCS=<one> DURATION=3s CONNECTIONS=64 SCENARIOS=<one> bench/load.sh`,
    one call per framework, GOMAXPROCS and scenario, after waiting for `CPU_Speed_Limit = 100`.
    There were three rounds, in forward, reverse and forward framework order. The version
    comparison used `FRAMEWORKS=owlkei LOGS=on` with five rounds at GOMAXPROCS 1 and 2 and four
    rounds at all cores, alternating `9b130a4` and `0cdeef1`.
  - Benchmarks: `go test -c` once per commit, then six alternating rounds of
    `-test.bench . -test.benchmem -test.cpu 1,2 -test.count 1` in `internal/logpipe`, and of
    `-test.bench 'Admitted|_Shed$'` in `middlewares/loadshed`, then `benchstat`.
- **No `bench/` changes** in this step.

- **The GOMAXPROCS 1 tail is gone.** 0005 measured 95 ms (Static) and 142 ms (Chain) against 4-6 ms
  for the others. Owlkei Go is now 4.5 and 6.7 ms against 4.0 and 4.5 ms, within the roadmap's
  2× target (1.1× and 1.5×).
- Across all 16 Owlkei Go runs at GOMAXPROCS 1 with the log on (this table plus the version batch
  below), the p99 was under 18 ms in 15. One run reached 127 ms: Static, version batch round 2, at
  14.7k requests per second. That batch ran at a load average of 4-7. The same rounds had other
  10-15 ms runs, and other frameworks had their own 30-70 ms outliers in the quieter batch. It is
  counted as noise, but it is the one run that looks like the old tail. The medians at
  GOMAXPROCS 1 were 1.1-1.5× the best other framework in the quiet batch and 9-12 ms in the busier
  version batch.
- At 12 cores Chain is 3.9 ms against Echo's and Chi's 3.0 ms. Owlkei Go serves 25 % more requests
  there, and the gap was the same in 0005 (3-6 ms for everyone).

**Lines written:** in every run with a logger, of every framework, the log file gained between
33 and 62 lines more than the requests `wrk` counted (the requests still in flight when `wrk`
stops). There were two exceptions, both Owlkei Go at 12 cores, listed below. No run at GOMAXPROCS 1
or 2 wrote fewer lines than requests, and none had a `LogDropped` record.

**`LogDropped` records:** 2 of the 14 runs of `9b130a4` at 12 cores with the log on had them:

| Run | Requests | Lines | `LogDropped` records | Info lines reported dropped |
|---|---|---|---|---|
| round 2, Static | 297,161 | 296,693 | 2 | 507 (0.17 %) |
| round 3, Chain | 239,397 | 237,833 | 2 | 1,624 (0.68 %) |

In both runs the two records were 60 ms apart (for example 19 lines, then 1,605). That fits an
output stall that holds more than the soft limit (about 820 KiB, or about 25 ms of access lines
at 77k requests per second) while the request goroutines keep writing. It is rule P7 working as
designed, and the counts add up: the missing lines equal the reported drops less the usual
in-flight surplus. A follow-up batch of 16 alternating runs at 12 cores, 8 per commit, had no
drop at either `9b130a4` or `0cdeef1`. With 2 of 14 runs at `9b130a4` and 0 of 8 at `0cdeef1`,
the sample is too small to call it a change. The roadmap Log saw drops at `0cdeef1` as often.

**Bytes per line** are unchanged: Owlkei Go's access line is about 270 B for Static and 450 B for
Chain (trace ID, request ID, client IP and stage times). Gin writes about 125 B, Echo 150 B, Chi
105 B (text) and Fiber 130 B.

- **`loadshed`:** the adaptive admitted path costs 40 ns at 1 and 2 CPUs, under the roadmap's
  60 ns bound (step 3) and below `0cdeef1`. The roadmap Log measured 52 ns, and 0005 measured
  49-50 ns while throttled. The probe slots and the waiter order cost nothing measurable on the
  admitted path. With a body, the cost is within the noise: the one 37 % spread is a single slow
  round. The body wrapper grows from 48 B to 64 B, the next size class, and stays at one
  allocation, as in the roadmap Log.
- **`logpipe`:** the changes match design 0016's measurements and its accepted open question 4.
  `Async_1` is one goroutine writing in a tight loop. There the writer only runs at preemptions,
  so batches grow and the queue's buffers are larger (+16 ns, about 125 B more per op, amortized). Real
  servers write from many goroutines (`Async_12`), and that case is unchanged. The synchronous
  path is 20 % faster. `Async_12` at GOMAXPROCS 1 still drops 99 % of its records by design: 12
  writers on one core outrun a writer that gets the core only at preemptions. At GOMAXPROCS 2 it
  drops 21 % (`0cdeef1`) and 36 % (`9b130a4`), a difference within the spread (p = 0.18,
  ±83-187 %). The load test above, with real request goroutines, dropped nothing at 1 and 2
  cores.

## What is left

- **Log-off overhead:** Owlkei Go with its log off is still 74-85 % of net/http (Gin, Echo and Chi
  88-99 %), 5-7 µs of CPU per request at 1-2 cores. This is the request scope and the reflection
  floor from 0005 (721 B per Static request). With the log on, Owlkei Go now leads or is within
  11 % of the best of Gin, Echo and Chi, so this is the largest remaining gap at small core counts.
- **Chain at 1-2 cores:** 89-93 % of the best other framework with logging on. The longer access
  line (450 B with the stage times) is the visible difference.
- **`LogDropped` at 12 cores:** worth a longer run at both commits (30 s or more, several rounds)
  to see whether the 1 ms batching changes how often an output stall crosses the soft limit. The
  short runs here can't tell.
- **One 127 ms p99 at GOMAXPROCS 1** in 16 runs. If it shows up again on a quiet machine, take a
  runtime trace of the run, as in 0005.
- **Measurement:** the cool-run method (3 s runs that start at a 100 % speed limit, best of
  several, alternating order) kept the comparisons usable. A desktop or a cloud VM with fixed
  clocks would still make medians, not only best runs, comparable.
- Unchanged from 0005: 0003 H1 / H2 (pooled encoders, shared header slices), L2, L3, L6, L10, the
  HTTP half of L8.
