# HTTP report 0008: server-rendered pages

Roadmap `docs/roadmap/0008-server-rendered-html.md`, step 9. Benchmarks in `bench/page_test.go`.

## Method

- `BenchmarkOwlkeiPage`: one app with `helmet` bound and `EnableRender`, two routes answering the same
  data (10 booking rows): `GET /json` returns it as JSON from a `owlkei.HTTP` controller, `GET /bookings`
  renders it as a page from a `owlkei.Page` controller (a layout with a stylesheet through `{{asset}}` and
  an inline script with `{{nonce}}`, a 10-row table, about 1.7 KB of HTML). Through `App.ServeHTTP` with
  `httptest`, so no network.
- `BenchmarkOwlkeiPageIdleMemory`: live heap after two GCs, an app without `EnableRender` against the same
  app with it and one page.
- Go 1.27.4, Intel Core i7-9750H, 12 threads, 6 runs, `benchstat`, machine quiet (load average about 2.5).

## Results

| | Time | Bytes/op | Allocs/op |
|---|---|---|---|
| JSON route, 10 rows | 8.2 µs ± 2 % | 5.5 KiB | 40 |
| Page route, 10 rows, layout, nonce | 62.6 µs ± 1 % | 16.6 KiB | 448 |

| Idle heap | |
|---|---|
| App without `EnableRender` | 10.7 KiB |
| Same app with `EnableRender` and one page | 35.4 KiB (+24.7 KiB: parse trees, the asset table, the page table) |

- An allocation profile of the page route puts 92 % of its allocations inside `html/template` execution
  (`reflect.Value.call` of the escapers, `htmlReplacer`, `walkRange`). The framework's own share
  (`writePage`, the pooled buffer, `helmet`'s nonce form, the context) is under 10 allocations.
- Design 0018 estimated 10 to 40 µs and 100 to 400 allocations for a page of about 4 KB; the measured page
  is smaller and costs more, because every `{{.Field}}` in a `range` goes through `html/template`'s
  reflection-based escaper chain. That is the price of contextual escaping, which the roadmap requires.
- Nothing runs while idle: no goroutine, timer or watcher, with or without `IsReload`.

## API routes against the start of the roadmap

`bench/` `BenchmarkOwlkei/*` (no `EnableRender`), test binaries of `402b10f` and of the working tree run
alternately, 8 rounds, the order swapped every round so warm-up and heat favor neither:

| Scenario | Before | After | p | Bytes and allocs |
|---|---|---|---|---|
| Static | 1.23 µs | 1.26 µs | 0.44 | equal |
| Param | 2.84 µs | 2.91 µs | 0.86 | equal |
| Query | 4.04 µs | 4.11 µs | 0.59 | equal |
| JSONBody | 5.98 µs | 6.10 µs | 0.80 | equal |
| Chain | 3.47 µs | 3.68 µs | 0.20 | equal |
| Exception | 2.12 µs | 2.45 µs | **0.005** | equal |
| NotFound | 1.08 µs | 1.09 µs | 0.72 | equal |

- Only Exception moved significantly (+16 %, about 330 ns). The scenario panics a `BadRequestException`
  without a cause, so nothing is logged; a CPU profile diff of the two binaries shows no framework function
  costing more, only runtime noise (`madvise` against `kevent`). It needs a rerun on a quiet machine with
  `-count 10` before acting; the candidate is the R24 client-text computation on the error path.
- Bytes and allocations per request are identical in every scenario.

## Binary size

`go build ./sample` (the existing sample app, which does not render pages): 15.6 MB before, 17.1 MB after
(+1.4 MB): `html/template` is linked into every app once `internal/core` imports it, as design 0018
expected (about 1 MB).

## Follow-ups

- If page throughput matters (the court booking app will tell), the candidates are in the template engine,
  not the framework: fewer actions per row (pass pre-formatted strings), or caching rendered fragments of
  pages whose data rarely changes. Both are application choices; neither needs a framework change now.
- `loadshed`'s 503 for a browser renders the error page; its cost is the built-in page (no template
  execution for the built-in page) and was not measured separately.
