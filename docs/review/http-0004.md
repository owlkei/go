# HTTP after roadmap 0004

Roadmap 0004 (trace context and logging) measured against `docs/review/http-0003.md`.

- **Machine:** the same Intel Core i7-9750H laptop (`Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz`, 12
  logical CPUs). It was **not quiet**: a browser renderer used about one core for the whole run, and
  the load average was 4-9 during the Go benchmarks and 10-18 during the load test. Absolute
  numbers are 1.4-2× those of the 0003 report (net/http Static 222 ns instead of 114 ns), with
  spreads up to ±40 % per row. Only same-run comparisons count. The 0003 column below is commit
  `6de9f6f` (0003's measured commit) measured again in this run in a git worktree, alternating with
  the current commit round by round.
- **Go:** 1.27.4, darwin/amd64. **Commit:** `ac59463` (after step 7 and the review fixes).
- **Rerun:** `make bench-compare`, `FRAMEWORKS="nethttp ginject gin" DURATION=5s CONNECTIONS=64 make load`,
  and the scratch module described under "Access log on and off".

p ≥ 0.15 on most rows). The table comes from a second run: 10 alternating rounds of Ginject,
net/http, Gin and Echo, `benchstat` of `6de9f6f` against `ac59463`. net/http, Gin and Echo did not
change between the two builds (p ≥ 0.22 in every scenario), so the Ginject change is the
framework's.

`make bench-compare` prints them.

**Where the cost comes from:** every request now pays +1 allocation and +528 B, the request scope of
steps 1-2. A memory profile of Static attributes it to `net/http.(*Request).WithContext` (the
request copy that carries the scope, about 320 B) and `tracecontext.NewRequest` with its
`traceparent` (about 210 B). The roadmap Log estimated it on a quiet machine at +270 ns for Static
(615 → 884 ns); on this loaded machine it shows as +600 to +800 ns (core `BenchmarkServeHTTP_Static`
969 → 1,590 ns, p = 0.008), because the extra garbage also costs GC time. The `NotFound` goal of
0003 (within 1.5× of net/http) still holds at 0.88×.

**Trace listener and incoming `traceparent`** (core benchmarks, same run, 5 rounds): Static with a
listener is 1,786 ns, 8 allocs, 640 B (one more allocation and 16 B than without, for the span IDs);
Static with a valid incoming `traceparent` is 1,461 ns, 7 allocs, 624 B (no extra cost for continuing
a trace). With no listener, spans cost nothing extra, as step 3 required.

rounds. Requests per second are about half the 0003 figures because of the machine load (the load

ran right after, for a same-machine comparison.

## Log call cost

`log` benchmarks of one JSON line with four scalars. At HEAD they are the package's own
`BenchmarkLog_Info_Scalars_JSON_Async_*` and `BenchmarkLog_Info_SlowOutput_*` (asynchronous sink).
For `6de9f6f`, the same bodies were added in the scratch worktree on the synchronous logger
(`newLog(out, …)`), under the same names. Five alternating rounds, p ≤ 0.032 for every row,
3 allocations per call in both builds.

| Case | `6de9f6f` | Now | Change |
|---|---|---|---|
| Free output (`io.Discard`), 1 goroutine | 1.95 µs, 144 B | 2.32 µs, 378 B | +18 % |
| Free output, 12 goroutines | 580 ns, 144 B | 1,077 ns, 462 B | +86 % |
| Slow output (2 ms per write), 1 goroutine | 2,267 µs | 2.26 µs | −99.9 % |
| Slow output, 12 goroutines | 2,260 µs | 0.56 µs | −99.98 % |

- A slow output no longer reaches the caller: a line costs the same 2.2 µs whatever the output does.
  Before, every caller waited for the write, and 12 goroutines queued on one mutex.
- On a free output the pipeline costs more than the old mutex around `io.Discard` (which made no
  system call). At 12 goroutines that is +500 ns per line on this loaded machine (the Log's L10
  measured about +100 ns on a quiet one): the queue's mutex and the writer's wake-ups. The extra
  bytes are the second batch buffer that bursts allocate again (accepted in the Log for the smaller
  idle footprint).
- **`From`:** 5.7 ns with no scope in the context, 8.7 ns once the scoped logger is cached in the
  scope, 425 ns and 4 allocations (536 B) for the first call on a scope. A scoped `Info` is 1.09 µs
  and 1 allocation on the built-in logger (synchronous, `io.Discard`) and 168 ns and 2 allocations
  through an adapter.

## Access log on and off

`bench/` still has no access log switch, so the scenarios were rebuilt in a scratch module outside
the repository, built once against each commit: the same controllers as `NewGinjectApp`, Static
and Chain, single goroutine and `RunParallel` (12 goroutines), access log off and on, with two
loggers: the silent adapter of the 0003 measurement, and the built-in JSON logger with stdout
redirected to `/dev/null` (its pipeline running, as after `Create`). Five alternating rounds,
p = 0.008 for every row.

Built-in logger (the default case):

| Scenario | Off now | On now | Extra now | Extra at `6de9f6f` | Target (design 0010) |
|---|---|---|---|---|---|
| Static | 1,486 ns, 7 allocs | 9,564 ns, 12 allocs, 9.0 KiB | +8.1 µs | +0.9 µs (worker) | +1 µs: **not met** |
| Chain | 3,800 ns, 19 allocs | 15,140 ns, 28 allocs, 5.5 KiB | +11.3 µs | +3.0 µs (worker) | +2.5 µs: **not met** |
| Static, 12 goroutines | 1,017 ns | 4,471 ns | 4.4× | 2.8× | none |
| Chain, 12 goroutines | 2,269 ns | 9,583 ns | 4.2× | 1.6× | under 2×: **not met** |

Silent adapter (as in 0003):

| Scenario | Extra now | Extra at `6de9f6f` |
|---|---|---|
| Static | +1.8 µs (18 allocs) | +1.0 µs |
| Chain | +4.4 µs (42 allocs) | +2.8 µs |
| Static, 12 goroutines | 2.2× | 2.9× |
| Chain, 12 goroutines | 2.2× | 1.8× |

The line is now formatted on the request goroutine (design 0012: no worker), so the whole cost is
the request's. At `6de9f6f` the worker formatted it on another goroutine and dropped lines when it
fell behind, so the old "extra" is only part of the old cost. Even so, the built-in path is far over
the step 5 estimate (3.8 µs and 4 allocs for a 6-stage line). Profiles show two causes:

- **Buffer churn:** `logpipe.grow` is 68 % of the bytes. When the writer has taken the queue's
  buffer, the next line finds none and allocates a new `keepCapacity` (64 KiB) buffer. With a fast
  output the writer takes it after almost every line, so about one line in seven allocates 64 KiB
  (8.6 KiB per request on average). The Log's "+25-50 B per call" came from shorter lines and
  different timing.
- **One writer wake-up per line:** with a fast output the writer is idle, so each line signals it
  (`pthread_cond_signal`, `usleep` and `pthread_cond_wait` are the top three CPU entries).

Both are "Open" in the "What is left" section below. The silent adapter path is mostly the 16 allocs
of the adapter access line (L3, kept).

### Follow-up: buffers kept, CPU per written line (2026-11-17)

Two changes after the numbers above, approved by the maintainer: the sink keeps both batch buffers
(up to 64 KiB each) when the queue empties and grows an empty one from 4 KiB, and Pretty draws the
stages as a tree again (Pretty only). Static with the access log: 9.0 KiB → 1.9 KiB per request.

The table above compares two different amounts of work. The `6de9f6f` worker dropped any line it
could not keep up with (`select … default`), so it wrote few of them. Measured again in production
settings (JSON format, a real file or a pipe read by `cat`, 200,000 requests, one goroutine,
GOMAXPROCS 1 and 2) as the process's whole CPU time (user + sys) per request, and counting the
lines that reached the output (median of 3):

| Scenario | `6de9f6f`: extra CPU | lines written | per written line | Now: extra CPU | lines written |
|---|---|---|---|---|---|
| Static, 1 CPU, file | +1.7 µs | 8 % | 21 µs | +3.9 µs | 73 % |
| Static, 1 CPU, pipe | +2.0 µs | 12 % | 17 µs | +4.1 µs | 80 % |
| Static, 2 CPU, file | +2.7 µs | 10 % | 27 µs | +7.0 µs | 100 % |
| Static, 2 CPU, pipe | +2.6 µs | 16 % | 17 µs | +7.0 µs | 100 % |
| Chain, 1 CPU, file | +6.8 µs | 19 % | 36 µs | +8.3 µs | 88 % |
| Chain, 1 CPU, pipe | +6.9 µs | 21 % | 32 µs | +9.2 µs | 94 % |
| Chain, 2 CPU, file | +8.7 µs | 17 % | 52 µs | +15.4 µs | 100 % |
| Chain, 2 CPU, pipe | +7.5 µs | 21 % | 36 µs | +12.4 µs | 100 % |

- **A written line costs 3-5× less CPU than before** (Static: 17-27 µs → 5-7 µs; Chain: 32-52 µs →
  10-15 µs). The old "+0.9 µs" was the price of losing 80-90 % of the lines under load, silently.
  Now a benchmark that saturates one CPU drops some Info lines above the soft limit, by design, and
  counts them in `LogDropped`.
- The design 0010 targets (+1 µs, +2.5 µs) measured that dropping worker and are retired; the
  comparison is CPU per written line.
- On 2 CPUs a line costs about 3 µs more than on 1: the writer runs on the second core and is woken
  for almost every line (thread wake-ups and scheduler spinning). Batching with a short delay would
  remove most of it; it is in the backlog with these numbers, not needed for 0004.
- Pretty (development only): a 6-stage access line 6.0 → 8.3 µs and 21 → 39 allocs for the tree
  (JSON unchanged at 4.2 µs, 4 allocs; the old reflection shape was 17 µs).

On one or two vCPUs the writer shares the core with the requests. A log call still costs about
2.3 µs and never waits for the output.

`ServeHTTP_StaticParallel` scales only 2× from 1 to 12 cores. Its CPU profile is mostly GC and
scheduler time (`usleep`, `madvise`, `pthread_cond_*`) from the extra 528 B per request, plus 15 % in
`tracecontext.NewRequest`, where `readRandom` takes a global mutex (`putTraceID` and `putSpanID`
contend in `lockSlow`). In the scratch module, Static at 12 goroutines went from 216 ns to 900 ns.

**Idle cost of an app with the access log on** (scratch module, built-in logger; the second app in
the process, after a first one paid the one-time package setup):

| | `6de9f6f` | Now |
|---|---|---|
| Heap after `Create` | +139 KiB | +24 KiB |
| Goroutines after `Create` | +1 (the worker) | +0 |
| Heap after 1,000 requests and 1.5 s idle | +188-197 KiB | +48-224 KiB (GOMAXPROCS 1 to 12; kept batch buffers plus the pooled contexts; at most 2 × 64 KiB of buffers since the follow-up) |
| Goroutines then | +1 | +0 (the writer exits when the queue is empty) |

**Pipeline memory under a stuck output:** stdout replaced by a pipe that nobody reads, 12 goroutines
for 5 s, each alternating a request with the access log on, an Info line, a Warn line (both with
200 B of padding) and an Error line.

- **Now:** 6.0 million calls; no caller blocked: the slowest took 102 ms, which is the 100 ms bounded
  wait of Error when the queue is full. Heap in use after GC: +1.5 MB (the design's worst case is
  about 2.1 MiB per output: `queueLimit` 1 MiB plus the batch buffer). The peak between two GCs was
  +8.2 MB, which is mostly garbage of the encoders and requests. No goroutine was left over.
- **`6de9f6f`:** the first write blocked, and every goroutine stayed parked in `sync.Mutex.Lock`
  until the 20 s test timeout.

## What is left

**Open, measured in this review:**

- **Access log cost on the built-in logger:** resolved by the follow-up above (buffers kept; the
  comparison with `6de9f6f` was per request against a worker that dropped most lines). Left: one
  writer wake-up per line on two or more CPUs (about +3 µs), in the backlog.
- **Request scope cost:** +1 allocation and +528 B on every request (the `WithContext` copy and the
  scope). Its GC share makes it +600-800 ns under load. The parallel path also contends on the
  ID generator's global mutex. The Log's open idea (one locked read for the trace tail and the
  request ID) halves the lock handoffs. A per-P or batched random source would remove them.
  Avoiding the request copy would change what `r.Context()` returns to middlewares.
- **Log calls on a free output at 12 goroutines:** +500 ns per line against the old mutex (L10,
  kept; +100 ns on a quiet machine).

**Kept review findings** (roadmap Log): L2 (`NewTraceID` at 12 goroutines is 112 ns, not on the
request path), L3 (an adapter access line costs 16 allocs on the request goroutine), L6 (the Fatal
tests wait 2 s), L10 (contention, above), the HTTP half of L8 (about 2 ns; a fix would widen the
public API).

**Deferred heavy techniques** (`docs/roadmap/backlog.md`, waiting for approval): 0003 H1 (one scratch
buffer and a kept JSON encoder per pooled context) and 0003 H2 (shared read-only header value
slices), unchanged since 0003.

**The reflection floor:** unchanged. `reflect.Call` is still most of the Static gap to net/http,
together with the request scope now. Design 0006 Q1 stands.

**Backlog for roadmaps 0005 and 0006:**

- 0005 (middlewares, guards, built-in modules, security audit): review `guards/throttler`, which the
  README's production section now recommends against panic floods, with the rest of the guards. The
  Public API surface roadmap follows 0005.
- 0006 (WebSocket): the framework's WebSocket error lines without `trace_id` or `connection`
  (`WSReadFailed`, `WSWriteFailed`, `WSPingSendFailed`), the own RFC 6455 / 7692 implementation, and
  the 0003 leftovers: `common.NormalizeRecovered` in the WS read loop, hijacked connections not
  closed by graceful shutdown (0008 G10), and no trace event for the WS handler stage (0006 B15).
