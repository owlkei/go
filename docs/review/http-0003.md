# HTTP after roadmap 0003

Roadmap 0003 (server and production) measured against `docs/review/http-0002.md`.

- **Machine:** the same Intel Core i7-9750H laptop (`Intel(R) Core(TM) i7-9750H CPU @ 2.60GHz`). It
  ran cooler than for 0002 (net/http's Static benchmark was 114 ns instead of 147 ns), so the
  absolute numbers of the two reports can't be compared directly. The 0002 column below is commit
  `6a2767f` measured again in this run, in a git worktree, alternating with the current commit
  round by round to limit thermal drift. On the cooler machine it is up to 23 % faster than in the
  0002 report (Static 786 against 793 ns, Chain 2,695 against 3,123 ns).
- **Go:** 1.27.4. **Commit:** `9d5959b` (after step 5 and the review fixes).
- **Rerun:** `make bench-compare`, `FRAMEWORKS="nethttp owlky gin" DURATION=5s CONNECTIONS=64 make load`.

## Go benchmarks: the framework's own cost

Median of 5 runs, `benchstat` of `6a2767f` against `9d5959b` (p = 0.008 for every Owlky Go row).
net/http did not change between the two runs (p ≥ 0.056 in every scenario but NotFound, −0.7 %).

The "was" ratios are `6a2767f` against net/http in this run. Chi and Fiber ran too (Static 315 ns
and 518 ns, NotFound 502 ns and 1,041 ns); `make bench-compare` prints them.

Bytes per request fell in every scenario: Static 184 → 160 B, Exception 369 → 320 B, NotFound
737 → 112 B, the others 1-3 %. The raw `benchstat` inputs are not committed; rerun the commands
above to reproduce.

**Goals of the roadmap:**

- NotFound within 1.5× of net/http (step 1): **met**, 0.55×. The 404 body is precomputed and the
  path no longer goes through the exception filters (4 allocations, 112 B).
- Access log on costs a bounded, measured amount (step 4): see "Access log on and off" below.
- The production checklist holds, each item tested (step 2): **met**, 18 of 18.

The other scenarios gained 4-15 % from removing the closures and the `MaxBytesReader` per request
in `ServeHTTP` / `handleRequest` and from 0003 H3 (capacity kept across requests). Exception gained
24 % from 0004 H1 (the hand-written error body).

## Load test

Two rounds of `make load` back to back, 64 connections, 5 s per scenario, mean of the two rounds.
Within a round the frameworks run one after another (net/http first), and round two was about 10 %
slower than round one for net/http, so the ratios carry a few points of noise (Static: 81 % in
round one, 88 % in round two).

| Scenario | Owlky Go | net/http | Gin | Owlky Go ÷ net/http now | at 0002 | at the baseline |
|---|---|---|---|---|---|---|
| Static | 104.4k | 123.6k | 104.7k | 84 % | 90 % | 93 % |
| Param | 94.1k | 102.7k | 98.9k | 92 % | 94 % | 91 % |
| JSONBody | 82.1k | 94.4k | 91.9k | 87 % | 88 % | 71 % |
| Chain | 92.0k | 100.4k | 91.2k | 92 % | 94 % | 90 % |

Requests per second are about twice the 0002 figures because that run was thermally throttled.
Over the loopback the network stack dominates: the ratios stay where 0002 left them, within the
noise of this run. Owlky Go is level with Gin on Static and Chain. Every run returned only 2xx.

## Access log on and off

`bench/` has no access log switch, so the scenarios were rebuilt in a throwaway module outside the
repository: the same controllers and silent logger as `NewOwlkyApp`, one app with
`EnableAccessLog()` and one without, Static and Chain, single goroutine and `RunParallel` (12
goroutines). Off and on alternate round by round; medians of 5 runs, p = 0.008 for every row. The
allocation counts include the worker's, which formats lines on another goroutine at the same time.

| Scenario | Off | On | Extra | Target (design 0010) | Result |
|---|---|---|---|---|---|
| Static | 652 ns, 6 allocs | 1,634 ns, 20 allocs | +0.98 µs | +1 µs | met (at the edge) |
| Chain | 2,260 ns, 22 allocs | 5,082 ns, 61 allocs | +2.82 µs | +2.5 µs | over by 0.3 µs |
| Static, 12 goroutines | 213 ns | 611 ns | 2.9× | none | - |
| Chain, 12 goroutines | 1,274 ns | 1,990 ns | 1.56× | under 2× | met |

These agree with step 4's numbers in `accesslog/README.md` (+1.1 µs, +2.7 µs, 1.55×). Two notes:

- The parallel "on" runs exceed the worker's rate (about 65,000 lines per second), so the queue
  fills and lines are dropped: that is why their allocations per request (8 and 28) are lower than
  the single-goroutine ones. They measure the request goroutines' cost with a saturated logger,
  which is the case the design bounds.
- The "at most 2 extra allocations on the request goroutine" target can't be read from these
  benchmarks, which count the worker too; `BenchmarkAccessLog_Request_*` in `accesslog` remains
  the measurement for it.

## What is left

**Open review finding L1:** a non-exception panic captures a stack of up to 4 KiB for the log
(0007 E3). `BenchmarkServeHTTP_PanicString` is 26.3 µs, 7.3 KiB and 11 allocations per panic,
against 1.25 µs for an exception. Under a flood of requests that panic, nothing bounds the total:
each one pays the capture and the log line. A rate limit or a sampled capture (for example, a full
stack for the first panics per interval, the value only after that) would bound it; not designed
yet.

**Deferred heavy techniques** (designed in roadmap 0002, in `docs/roadmap/backlog.md`, waiting for
the maintainer's approval):

| Design | Technique | Expected effect |
|---|---|---|
| 0003 H1 | one scratch buffer and a kept JSON encoder per pooled context | JSON of a map 8 → 2 allocs; body read 0 allocs |
| 0003 H2 | shared read-only header value slices | −1 alloc and ~50 ns per response |

0002 H1, 0003 H3 and 0004 H1 were approved and built in this roadmap.

**The reflection floor:** handler calls go through `reflect.Call` (about 210 ns per call, measured
in 0002). Design 0006 Q1 accepted it for now, with no `unsafe` and no opt-in registration API. It is
most of the remaining Static gap to net/http (668 ns against 114 ns, with Gin at 157 ns). Removing
it needs an `unsafe` trampoline or an opt-in typed handler, both of which need approval.

**WebSocket, for roadmap 0005:**

- The WS read loop still uses `common.NormalizeRecovered`: a non-exception panic in a WS handler
  sends its text to the client (design 0007, observed, not changed).
- Hijacked WebSocket connections are neither waited for nor closed by graceful shutdown; closing
  them with a close frame belongs to 0005 (design 0008 G10).
- No trace event for the WS handler stage (design 0006 B15 kept in design 0010).
- The own WebSocket implementation that replaces `golang.org/x/net/websocket` (backlog: RFC 6455,
  then RFC 7692, Autobahn, fuzzing, benchmarks against `coder/websocket` and `gorilla/websocket`),
  with acks, backpressure, limits, hooks, shutdown and the broker.
