# HTTP after roadmap 0002

Roadmap 0002 (request hot path) measured against `docs/review/http-baseline.md`.

- **Machine:** the same Intel Core i7-9750H laptop. It ran hotter than for the baseline (net/http's
  Static benchmark was 22 % slower), so Owlky Go's gains below are a floor.
- **Go:** 1.27.4. **Commit:** `6a2767f` (after step 6).
- **Rerun:** `make bench-compare`, `FRAMEWORKS="nethttp owlky gin" DURATION=5s CONNECTIONS=64 make load`.

## Go benchmarks: the framework's own cost

Median of 5 runs, `benchstat` against the baseline run (p = 0.008 for every Owlky Go row).

| Scenario | Baseline | Now | Change | Allocs | net/http now | Owlky Go ÷ net/http |
|---|---|---|---|---|---|---|
| Static | 1,672 ns | 793 ns | −53 % | 13 → 9 | 147 ns | 5.4× (was 13.9×) |
| Param | 4,304 ns | 1,993 ns | −54 % | 27 → 19 | 1,397 ns | 1.4× (was 2.8×) |
| Query | 6,292 ns | 3,054 ns | −51 % | 46 → 28 | 2,501 ns | 1.2× (was 2.4×) |
| JSONBody | 9,252 ns | 4,831 ns | −48 % | 52 → 34 | 3,314 ns | 1.5× (was 2.8×) |
| Chain | 6,093 ns | 3,123 ns | −49 % | 40 → 25 | 1,869 ns | 1.7× (was 3.4×) |
| Exception | 6,398 ns ¹ | 2,252 ns | −65 % | 33 → 10 | 1,358 ns | 1.7× (was 5.7× ¹) |
| NotFound | 3,403 ns | 2,783 ns | −18 % | 31 → 23 | 1,381 ns | 2.0× (was 3.2×) |

1. From the first baseline run, which is the one `benchstat` compares against: Owlky Go's own
   Exception code path is the same in both, but in that run the other frameworks still wrote the
   400 directly. The baseline report's Exception row (7,933 ns, 6.1×) comes from a second, hotter
   run made after the scenario was made fair; against it, Owlky Go's Exception is −72 %.

Bytes per request fell 15-62 % in every scenario (Static 304 → 184 B, Exception 980 → 369 B). The
raw `benchstat` inputs are not committed; rerun `make bench-compare` to reproduce.

**Goals of the roadmap** (not gates):

- Static under 1 µs: **met** (793 ns).
- Allocations halved in every scenario: **met only for Exception** (−70 %). The others fell 26-39 %.
  The remaining allocations are the ones the deferred heavy techniques remove (see below) and
  `core`'s request glue (roadmap 0003).

## Load test

The laptop was thermally throttled during the measurement (every framework ran at roughly 55 % of
its baseline requests per second), so absolute numbers can't be compared with the baseline. The
table compares Owlky Go with net/http on the same run: two interleaved rounds, 64 connections,
mean of the two rounds.

| Scenario | Owlky Go | net/http | Gin | Owlky Go ÷ net/http now | at the baseline |
|---|---|---|---|---|---|
| Static | 49.7k | 55.2k | 52.1k | 90 % | 93 % |
| Param | 46.6k | 49.8k | 49.8k | 94 % | 91 % |
| JSONBody | 40.5k | 46.2k | 45.0k | 88 % | 71 % |
| Chain | 44.9k | 47.9k | 48.5k | 94 % | 90 % |

Over the loopback the network stack dominates, so the framework's 2× gain shows up mainly where
Owlky Go's own cost was largest: JSONBody went from 71 % to 88 % of net/http's throughput. Every run
returned only 2xx.

## What is left

**Deferred heavy techniques** (designed, measured in the designs, not built: they need the
maintainer's approval):

| Design | Technique | Expected effect |
|---|---|---|
| 0002 H1 | the router appends parameter values to a caller-supplied buffer | −1 alloc per parameter route (Match_Param 203 → ~120 ns) |
| 0003 H1 | one scratch buffer and a kept JSON encoder per pooled context | JSON of a map 8 → 2 allocs; body read 0 allocs |
| 0003 H2 | shared read-only header value slices | −1 alloc and ~50 ns per response |
| 0003 H3 | `ParamValues` and the aggregation list keep their capacity across requests | −1 alloc per parameter request, −1 per interceptor request |
| 0004 H1 | a hand-written encoder for the fixed error body | error body ~500 ns / 2 allocs → ~55 ns / 0 |

**Roadmap 0003 (server and production):** the 404 path (2.0× net/http, 23 allocs), the closures and
`MaxBytesReader` per request in `handleRequest` / `ServeHTTP` (hot spots 6 and 7), the reflection
floor of handler calls (about 210 ns; an `unsafe` trampoline or an opt-in typed handler would need
approval), production defaults, and these findings from the run:

- `EnableDevtool` without `EnableVersioning` panics once a route exists.
- `SERVE_<x>_ANY` compiles to the glob `/<x>*/`, so it never serves `/<x>/...` (also before this
  roadmap).
- An interceptor that never calls `Pipe` still runs the main handler; a middleware panic skips the
  user's exception filters; a second `App` in one process answers 404 on its routes.
- The text of non-exception panics reaches the client through the default filter (security).
- Chain uses about 120 B more per request after step 6 with the same allocation count (suspected:
  `reflect.Call` copying the large controller receiver).
- `num.F64ToAnyNumOK` returns `any`, which allocates for floats and large integers during binding;
  typed helpers would remove it.
